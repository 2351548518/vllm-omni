## 经验 1：官方指南的参数不一定对，一切以实测为准

**你会遇到**：部署指南里建议某个采样参数，你严格照做，结果精度反而暴跌，怎么都想不通。

**为什么**：官方文档里的"参考值"和实际跑出来的最优值经常不是一回事。指南可能是旧版本写的，或者文档作者没实测。

**我们的真实案例**：部署指南 7.7.2 建议 Daily-Omni 用 `repetition_penalty=1.2`（一个控制 AI 说话不重复的参数）。我们严格照做，精度从 90/128（70%）暴跌到 76/128（59%），**掉了 10.9 个百分点**。反复做了 4 组对照实验（A→B→A→B），确认 1.0（代码默认值）才是对的。后来查官方 CI 脚本，用的也是 1.0——指南这段就是写错了。

**怎么解决**：①别盲抄指南的采样参数；②改参数前先跑 32 条小样本对照（新值 vs 默认值），谁高用谁；③确认有效再上全量。

**我们实测**：`rep=1.2` 全程 59%，`rep=1.0` 全程 77%+，差了 18 个百分点，一次就看清了。

## 经验 2：128 条子集会骗你，精度判断必须用全量

**你会遇到**：你只跑 128 条测试（为了省时间），结果 70% 左右，以为过不了准入，纠结好几天。

**为什么**：bench 客户端默认用随机种子打乱数据后取前 N 条。运气不好时，前 128 条恰好是最难的一批，代表不了整体水平。这是"抽样偏差"，不是你的代码有问题。

**我们的真实案例**：Daily-Omni 跑 128 条一直是 70.31%，我们以为离 77.5% 准入线差得远，整整纠结了两天。后来偶然跑了全量 1197 条，**实际是 77.94%，早就过了**。前 128 条恰好是偏难子集。

**怎么解决**：①精度结论必须用全量（1197 条也就多跑 30 分钟）；②或者至少跑官方同款的抽样方式；③子集只用来快速排错，不作结论。

**我们实测**：128 条 70.31% vs 全量 1197 条 77.94%，差了 7.6 个百分点，纯属抽样运气。

## 经验 3：配置改完了，先确认"真的生效"再花 NPU 时长

**你会遇到**：你改了 YAML 配置，重启服务跑测试，发现结果纹丝不动，白烧了半小时卡时。

**为什么**：vLLM-Omni 的配置项有严格的放置位置要求。放错位置不会报错，而是**静默忽略**——你改了个寂寞。

**我们的真实案例**：我们想把语音合成的 `token2wav_n_timesteps`（flow 采样步数）从 10 改成 3 来加速。第一次放在了 YAML 的 stage2 顶层，跑完 RTF 纹丝不动。查源码才发现：代码是从 `connectors.connector_of_shared_memory.extra` 这个嵌套位置读的，放 stage2 顶层根本不读。移到正确位置后，立刻生效（RTF -12%）。

**怎么解决**：①改完配置重启服务后，先 grep 服务日志确认"实际加载值"；②用我们的 `freeze_eval_identity.py` 工具，把 commit / 配置文件 / 结果全部算 SHA-256 冻结，每次实验前后对哈希，改没改进去一目了然；③先跑 1-2 条冒烟确认生效，再跑全量。

**我们实测**：配置放对位置后 RTF 从 0.44 降到 0.39，而放错位置时毫无变化——这个验证动作省了我们至少 2 小时无效卡时。

## 经验 4：远端环境不是 git 仓库，别指望 git 恢复文件

**你会遇到**：你在远端改坏了某个源码文件，想用 `git checkout -- file` 恢复，结果发现恢复出来的文件是错的，甚至更坏。

**为什么**：很多平台的 vllm-omni 是**解压的 tar 包**，不是 git clone。在非 git 目录里执行 git 命令，要么失败，要么**静默写入错误内容**（我们踩过：git show 把文件覆盖成了 2 行报错）。

**怎么解决**：①恢复文件一律从本地 git 仓库（`upstream/`）取；②用 base64 编码传过去再解码落地；③重大改动前先 `cp file file.bak` 手动备份。

**我们实测**：一次补丁回滚时，远端 `git show` 把 batched_token2wav.py 覆盖成错误内容，差点毁掉环境。之后统一从 Mac 本地 git 取原文件恢复，再没出过事。

## 经验 5：bench 客户端必须加 `--tokenizer` 本地路径，否则外网一断就崩

**你会遇到**：你跑 `vllm bench serve`，客户端启动时报 `Network unreachable`，然后 Connection reset，最后 `corrupted size` 崩溃，一条请求都没发出去。

**为什么**：bench 客户端默认按模型名（比如 `openbmb/MiniCPM-o-4_5`）去 HuggingFace 联网下载 tokenizer。评测环境外网不可达，它就崩了。

**怎么解决**：启动命令里**必须加**：
```bash
--tokenizer /workspace/shared_assets/models/OpenBMB/MiniCPM-o-4_5
```
指向本地模型目录，客户端就用本地 tokenizer，彻底绕开联网。

**我们实测**：加上这个参数前，三次跑都是秒崩；加上后，1197 条全量一次跑通。这个参数我们每条评测命令都带。

## 经验 6：WER 算不出来？两个条件缺一不可

**你会遇到**：Seed-TTS 的请求都成功了，但最后一步"计算 WER（转文字错误率）"报错：`Can't load processor for 'openai/whisper-large-v3'`，卡住不动。

**为什么**：WER 要用 Whisper 模型把生成的语音转成文字再对比。两个坑叠加：
①transformers 5.13 要求模型目录里有 `processor_config.json` 文件，但 whisper-large-v3 在 HuggingFace 上**根本没有这个文件**（只有 preprocessor_config.json）；
②非离线模式下，transformers 会先发网络请求，外网不通就直接失败，不会自动用本地缓存。

**怎么解决**（两步，缺一不可）：
```bash
# ① 在 HF 缓存里手动补一个 processor_config.json（内容一行）：
#    {"processor_class": "WhisperProcessor"}
# 路径：/root/.cache/huggingface/hub/models--openai--whisper-large-v3/snapshots/<hash>/

# ② 启动命令前必须设离线环境变量：
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1
```

**我们实测**：两个条件都满足后，WER 立刻算出来 = 0.0107（要求 ≤1.56），远超基线。之前卡了整整一小时。

## 经验 7：ASV 默认不计算！要环境变量显式打开

**你会遇到**：你跑完 Seed-TTS，结果里 `seed_tts_sim_evaluated = 0`，ASV（说话人相似度）是空的，以为代码坏了。群里也有人问"ASV 0.709 怎么复现不出来"。

**为什么**：vLLM-Omni 里 ASV 计算**默认是关闭的**（性能考虑），需要环境变量显式开启。不开就是 0 条，不是报错，很容易误判。

**怎么解决**：启动命令前设：
```bash
export SEED_TTS_SIM_EVAL=1
```
同时建议加 `--seed-tts-file-ref-audio`（用参考音频文件路径做音色对比，官方 cal_sim 同款思路）。

**我们实测**：加上 `SEED_TTS_SIM_EVAL=1` 后，ASV = **0.8430**（要求 ≥0.689，超过基线 0.709）。没加之前一直是 0。群里有人 baseline 跑不出 0.709，多半就是缺这个开关，或者参考音频路由有问题。

## 经验 8：flow 步数是你最容易拿到的"免费午餐"

**你会遇到**：你想优化 RTF（实时率，AI 生成语音的速度）和 TTFP（首包延迟），但不知道该从哪下手。

**为什么**：语音合成的最后一步（Token2Wav）内部要迭代 N 次精修波形，默认 10 次。步数越多越慢，但质量不一定更好。减少步数是纯系统级优化，**不动模型智力，官方允许**。

**怎么解决**：改 YAML（注意放对位置，见经验 3）：
```yaml
connectors:
  connector_of_shared_memory:
    extra:
      token2wav_n_timesteps: 3    # 10 → 3
```
再叠加一个组件通信优化（`connector_get_sleep_s: 0.001`，把轮询间隔从 10ms 降到 1ms）。

**我们实测**：10→3 步后：
- RTF：0.4423 → **0.39**（AI 说话比真人快）
- TTFP：986ms → **759ms**（首包快了 23%）
- **WER/ASV 完全不变**（精度零损失，逐条对比一致）
- 注意：2 步会启动失败（Engine core init failed），3 步是甜点。

## 经验 9：一次只改一个变量 + A→B→A + 哈希冻结，实验才可复现

**你会遇到**：你同时改了三个参数，跑出来的结果变好了（或变差了），但你**说不清是哪个参数起作用**，下次无法复现。

**为什么**：多变量同时改，变量互相干扰，结论无法归因。这是实验科学的基本纪律，评测场景尤其重要——你的优化要能说服评委"改了哪、为什么有效"。

**怎么解决**：
1. **一次只改一个变量**，其他全部冻结；
2. **A→B→A**：改前测 A → 改后测 B → 还原再测 A，确认 B 的变化可重复；
3. **哈希冻结**：用 `freeze_eval_identity.py` 把 commit、YAML、数据、结果的 SHA-256 存进 manifest，实验前后对哈希。

**我们实测**：靠这个纪律，我们一次实验就钉死了"rep 1.2 有害"（4 组对照），一次就确认了"flow 3 步精度无损"（WER/ASV 逐条对比一致）。没有对照的实验等于白跑。

## 经验 10：失败实验也是资产，把根因记下来

**你会遇到**：你改了个"看起来很有希望"的优化，结果服务 Segfault 崩了，或者启动失败。你默默回滚，然后忘了为什么失败——下次又踩一遍。

**为什么**：失败往往比成功更有信息量，但只有记下根因才有价值。很多坑（比如多 stage 流水线的缓存形状不一致）不记下来，三个月后自己都忘了。

**我们的真实案例**：
- E08 优化（cfg_rate=0 跳过无条件分支）：服务 Segfault。根因是 CFM 的 CNN/attention 缓存仍按双批 shape，而输入改成了单批，形状不匹配。
- flow 2 步：服务启动失败（Engine core init failed）。

**怎么解决**：每个失败实验都写一行"现象 + 根因 + 回滚方式"，汇总成踩坑合集。别人（包括未来的自己）看了就不用重复踩。

**我们实测**：我们的踩坑合集已经积累了环境类（远端非 git、外网不可达、SSH 超时）、参数类（rep 1.2、配置位置）、评分类（WER 离线、ASV 开关）、兼容类（transformers 5.13）十几条，接手的人 15 分钟就能上手。
